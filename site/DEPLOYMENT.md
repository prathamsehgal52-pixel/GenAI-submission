# Deploying Armoire

Armoire ships as one container image with two process types:

| Process | Command | Scaling |
|---|---|---|
| `web` | `node dist-server/index.js` (image default) | Stateless; run 2+ behind a load balancer |
| `worker` | `node dist-server/worker.js` | Run 1+; jobs are coordinated through Postgres |

Both need the same environment variables (see `.env.example`; every variable is documented there and validated at startup).

## 1. Provision

1. **PostgreSQL 14+** (managed: RDS, Cloud SQL, Neon, Supabase…). Enable automated backups with point-in-time recovery.
2. **Private S3-compatible bucket** (AWS S3, Cloudflare R2, GCS interoperability…). Block all public access. Create an access key scoped to that bucket with `GetObject`, `PutObject`, `DeleteObject` and `ListBucket`. If you serve images from a custom domain or region, `S3_ENDPOINT` must match it; the API adds that origin to its Content Security Policy.
3. **SMTP provider** (Postmark, SES, Resend…) for password resets and opted-in digests. Verify the `EMAIL_FROM` domain (SPF/DKIM).
4. **Anthropic API key** for garment recognition and stylist explanations (`ANTHROPIC_API_KEY`; model via `AI_MODEL`, default `claude-opus-5-5`). Requests use server-side refusal fallback.
5. **Product data** (one or both):
   - **eBay Browse API**: create a production keyset at developer.ebay.com, then set `EBAY_CLIENT_ID` and `EBAY_CLIENT_SECRET`, and add `ebay` to `PRODUCT_PROVIDERS`. Optionally set `EBAY_AFFILIATE_CAMPAIGN_ID` for eBay Partner Network links. Follow eBay's API License Agreement for display and attribution (the UI attributes listings to eBay and links to the item page).
   - **Affiliate feeds** (e.g. Awin): once approved by the advertiser, set `PRODUCT_FEED_URLS`, `PRODUCT_FEED_FORMAT` and `PRODUCT_FEED_ALLOWED_LINK_HOSTS`, and add `feed` to `PRODUCT_PROVIDERS`. Feeds are imported by the scheduled sweep.
6. **Optional:** set `SENTRY_DSN` and add `@sentry/node` to the image for error monitoring.

## 2. Configure

Required in production:

```
APP_ENV=production
APP_URL=https://your-domain        # must be https
DATABASE_URL=...
AUTH_SECRET=...                    # openssl rand -base64 48
STORAGE_DRIVER=s3  S3_BUCKET  S3_REGION  S3_ACCESS_KEY_ID  S3_SECRET_ACCESS_KEY  [S3_ENDPOINT]
EMAIL_DRIVER=smtp  SMTP_URL  EMAIL_FROM
TRUST_PROXY=true                   # when behind a load balancer (correct client IPs for rate limits)
ADMIN_EMAILS=ops@your-domain       # access to /app/admin
```

Integrations that aren't configured are reported to users as unavailable, never faked. `/app/admin` shows each integration's configuration and recent success or failure, queue depth, and 30-day AI usage with estimated cost.

## 3. Build and release

```bash
docker build -t armoire:$(git rev-parse --short HEAD) .
# Release step (once per deploy, before starting new web/worker processes):
docker run --rm --env-file prod.env armoire:TAG node dist-server/db/migrate-cli.js
# Run:
docker run -d --env-file prod.env -p 8787:8787 armoire:TAG                     # web
docker run -d --env-file prod.env armoire:TAG node dist-server/worker.js        # worker
```

Migrations are forward-only SQL files generated by `npm run db:generate` and are safe to re-run. Alternatively, set `MIGRATE_ON_START=true` on a single web instance.

## 4. Health, logs, monitoring

- `GET /api/health`: liveness (process up).
- `GET /api/health/ready`: readiness (database and storage reachable; 503 otherwise). Use it for load balancer checks.
- Logs are structured JSON on stdout. Cookies, authorization headers, tokens and signed URLs are redacted. Each response carries `x-request-id`.
- The worker prints `worker ready` once it is consuming jobs.
- Errors are reported to Sentry when `SENTRY_DSN` is set; otherwise they're logged with request context. Users never see stack traces.

## 5. Scheduled work

The worker registers these cron schedules (UTC) on start:

| Job | Schedule | What it does |
|---|---|---|
| `discovery-sweep` | `DISCOVERY_CRON` (default 06:00 daily) | Imports affiliate feeds, then queues a refresh for each user with 3+ items who hasn't had one in 20h. Refreshes are staggered to respect provider rate limits. |
| `maintenance` | 03:15 daily | Prunes expired rate-limit windows and discovery runs older than 30 days. |

Discovery is periodic, not continuous. Listings not re-verified within 7 days drop out of the feed unless saved. Digest emails go only to users who opted in, at most once a week, and only when strong new matches exist.

## 6. Security checklist

- HTTPS only (HSTS is sent). Session cookies are `Secure`, `HttpOnly`, `SameSite=Lax` in production.
- CSRF: state-changing API calls must come from `APP_URL`'s origin. Auth endpoints are protected by Better Auth's origin checks.
- Rate limits are stored in Postgres, so they hold across instances. They cover auth, uploads, styling, discovery refreshes, re-analysis and data export, plus a per-user daily AI cap (`AI_DAILY_USER_LIMIT`).
- Uploads are decoded and re-encoded (never stored as received), with size and pixel limits; EXIF/GPS is stripped.
- External product URLs must be https and on an allow-listed host. Feed fetching rejects private network addresses (SSRF).
- Every user-owned resource query is scoped to the session user; covered by `tests/server/authorization.test.ts`.

## 7. Backups and recovery

- **Database:** rely on managed PITR, with at least 7-day retention. Test a restore quarterly into a staging environment.
- **Object storage:** enable versioning with a 30-day noncurrent-version expiry so accidental deletions are recoverable and deleted user data ages out.
- **Account deletion** removes database rows (cascading) and photos immediately. Backups age out within their retention window; state this in your privacy notice (the bundled notice says 30 days).
- **Restoring from backup:** restore the database, point the app at it, then run migrations. Images referenced by restored rows must exist in storage (versioning covers this).

## 8. Local production smoke test

```bash
npm run build
APP_ENV=production APP_URL=https://localhost node --env-file=.env dist-server/db/migrate-cli.js
APP_ENV=production APP_URL=https://localhost node --env-file=.env dist-server/index.js
curl localhost:8787/api/health/ready
```
